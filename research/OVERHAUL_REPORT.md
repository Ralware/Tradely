## Baseline (2026-11-19)

Repository commit: `a8963ca`. Working tree was clean. Inventoried the repository,
read the analyzer, driver, tests, configuration, historical metadata and Python
imports. Research imports no backend or frontend execution modules. Its only
runtime third-party dependencies are NumPy and pandas; no dynamic strategy
imports or circular imports were found. Both dependencies are required. Root
and research dependency files serve separate installation scopes.

Executed `python -m pytest backend/tests research/tests -q -ra`: **287 passed**.
Ruff baseline: 57 findings (40 Optional annotations, 6 deliberate test import

analyzer, mostly pandas typing and optional exit-index narrowing.

The root pytest configuration previously selected only backend tests.
`research/data/` is git-ignored and absent from this checkout. Historical

No frozen strategy specification exists (also documented by the earlier

## Findings and implementation plan

1. **Critical correctness/integrity:** preserve trading behavior; optimizer
   resume identity omitted ranking choice and optimizer source. A torn JSONL
   append made the entire checkpoint unreadable. Input normalization reported
   duplicates/dropped records but the optimizer did not reject suspicious input.
2. **Performance:** every candidate reloaded CSVs, recomputed immutable cutoff,
   gap and HTF coverage information, wrote full reports into a temporary folder,
   then deleted them. Trade simulation repeatedly constructed heterogeneous
   pandas Series even for WAIT bars. Full indicators were computed twice.
3. **Reliability:** no process execution, pool-failure recovery, bounded queue,
   writer exclusion or atomic per-result checkpoint commits. Full results and
   a duplicate-tracking set grew with the search. Failed searches could be
   labelled complete and CLI exit status did not convey errors/interruption.
4. **Maintainability:** keep the authoritative analyzer and public driver;
   introduce a cohesive execution/storage helper, explicit prepared-data and
   worker result interfaces, lightweight dev tools, benchmark and test fixtures.
5. **Minor cleanup:** fix zero-valued ranking tie-breaks, finite/integer range
   validation, deterministic axis order, exact factorized valid counts. Retain
   historical sources in Git and all historical data/results/tests/manifests.

Implementation order: baseline and profile; analyzer preparation/no-output
interface with equivalence; bounded spawn executor and parent-only storage;
recovery and resume tests; lint/type/coverage/compilation; 20-candidate benchmarks;
documentation and hash verification. No full search is launched.

## Preservation policy

No existing dataset, historical result, test fixture, source file or integrity
manifest is deleted or moved. The original `FILE_HASHES.json` remains a historical
snapshot; a separate manifest records new source hashes. Existing output trees
are never reused for a new engine version. Uncertain cleanup candidates are
retained. Generated bytecode is not evidence of unused source.

## Implemented architecture and behavior

The existing analyzer remains authoritative. The driver generates and validates
candidates, then the runtime initializes private prepared data once per worker.
The analyzer computes indicators/convergence, signals, trades and metrics; workers
return compact structured evaluations. Only the parent commits atomic records,
checkpoint summaries, CSVs, metadata, logs and explicitly requested audits.

Performance changes are limited to removing redundant work: skip constructing
pandas rows for WAIT signals, reuse immutable cutoff/coverage/gap data, avoid a
second full indicator calculation, cache at most two indicator/warm-up frames per
worker using every relevant period, and bypass presentation output during search.
The actual Wilder/EMA arithmetic, signal predicates and trade execution arithmetic
are retained. No alternate simulator or cost model was introduced.

Execution uses a genuine spawn ProcessPoolExecutor for 2+ workers, with a default
of four and at most eight submitted tasks at that default. One worker is the
in-process reference. Each process owns data and a bounded cache; no full market
frames or ordinary trade histories cross the queue. Numerical child thread limits
are set before import and restored in the parent. No nested pools are permitted.

Durable per-candidate JSON records are the recovery source. Checkpoint summaries,
CSV and legacy JSONL exports are derived. Result files are sharded and read lazily;
only top-N candidates are retained for ranking. An OS-owned writer lock excludes
another parent and releases even on process death. Failed attempts retain type,
message, traceback, parameters, ID, PID and timestamp. Retry history is retained.
Hard termination cannot label uncommitted tasks successful. Graceful interruption
drains already-running tasks, which may take a candidate duration.

Resume identity now includes ranking filters, optimizer source and dependency
versions as well as data, engine, ranges, cutoff and verification policy. A named
resume reports incompatible fields. Original v1 checkpoints remain preserved;
resuming them under changed source is intentionally rejected.

Exact default valid counts: 9,827,470,540,800 (2H/4H), 5,688,896,716,800 (1D).
Invalid EMA prefixes are pruned before generating their suffixes. Search generation,
counting and canonical ordering do not materialize the Cartesian product.

## Correctness evidence

The pre-change analyzer was copied outside the repository before any source edit.
Its hash is recorded in `tests/fixtures/original_engine_golden.json.gz`. Goldens
were generated with its actual functions, not a second strategy implementation:
23 configurations covering all three timeframes, including 20 exhaustive-prefix
2H candidates with nonzero trades, plus each timeframe's baseline configuration.

The regression suite compares exact float64 indicator-array digests, exact signal
and reason strings, full trade dictionaries, all metrics excluding the intentionally
changed source fingerprint, and baseline per-bar audits. No numerical tolerance
was needed. Run IDs are held constant/normalized solely for cross-engine comparison.
For each of 1/2/4 workers, all 20 2H configurations also compare complete trades and
metrics against those original goldens. Additional 4H/1D parallel runs match the
original baseline metrics. Separate tests vary every cached indicator parameter
and compare cached/fresh outputs exactly. Baseline configuration dictionaries and
prepared input frames remain unchanged after evaluation.

All earlier cutoff, signal, ADX/DI/ATR, stop/target, gap priority, Chandelier,
time-stop, sizing, exposure and hypothetical-short regression tests are retained.
The optimizer's stricter rejection of malformed/duplicate/unordered data is an
input-admission improvement requested by the specification, not a trading-rule
change. The legacy analyzer loader continues its documented normalization behavior.

## Cleanup and dependency decisions

Removed the now-unused private `_gross_model_error` helper after verifying it had
no callers, consolidated the duplicate ranking key, and removed three unused test
fixture assignments/calculations. Kept public JSONL/ranking helpers for Python API
compatibility. Existing documentation was consolidated into the research README;
the optimization README now explains artifact ownership and links to it.

No original file was deleted or moved. Historical result datasets, metrics, audits,
logs, checkpoint and manifests remain byte-for-byte unchanged. No Git history was
rewritten. Runtime requirements remain only NumPy and pandas; their bounds now
match the root project. Ruff, mypy, pytest/coverage, pandas stubs and psutil live in
the separate development requirements. psutil is used only for benchmark/test
instrumentation, not by the optimizer. Bytecode and tool caches are ignored going
forward; pre-existing tracked caches are retained rather than making an unrelated
repository-wide deletion.

## Remaining limitations and readiness

**Verdict: ready for controlled testing.** Exact equivalence to the original
implementation is demonstrated on deterministic fixtures. The absent frozen
specification prevents independent certification of intended strategy parity;
the absent original BTCUSDT files prevent historical dataset reruns and market-data
performance claims. Diagnostic benchmark output remains explicitly unverified.
Windows is tested; Linux/macOS spawn/POSIX locking is implemented but not executed
on those operating systems. No full search was launched.

The default full Cartesian product is impractical even with this improvement.
Millions of atomic files and linear resume scans need further measurement; no
unlimited-scale or database-free scalability claim is made. Cache benefits depend
on repeated indicator periods, so a different parameter ordering/workload can
reduce speedup. External threads must not call run_search concurrently. In-flight
jobs have no forced timeout; hard-kill recovery relies on committed records.

Random, coarse-to-fine and staged search may help coverage but would need explicit
methodology identities; they are not silently substituted for exhaustive search.
Walk-forward, held-out selection and multi-period stability analysis remain future
orchestration work, with separate hashed datasets and warm-up design. Rankings
are in-sample screening outputs, not validated investment recommendations.
Numba, GPU, memory maps and alternative numeric simulators were deferred because
safe reuse and reduced I/O already provide measured benefits without new runtime
dependencies or numerical reassociation.

Exact PowerShell and Linux commands for smoke, 1/2/4 workers, limited search,
resume/retry, explicit full search and benchmarks are in [README.md](README.md).

## Final performance measurements

Final timings were run sequentially after tests, without concurrent test/lint work. Same seed-42 6,000-bar 2H fixture, 500 daily HTF rows, diagnostic cutoff, deterministic parameter prefix, source version and runtime. Windows, Python 3.14.6, pandas 2.3.3, NumPy 2.5.3; 8 physical / 16 logical CPUs and 23.29 GiB installed RAM. The target is a 16 GB machine; measured optimizer RSS remained far below that budget, but no real-market memory claim is made.

All numbers include initialization and parent outputs. Original sequential calls the pre-change analyzer and writes its full reports/audits each time, matching the old driver behavior. Refactored runs call the same trading logic with compact optimizer reporting. The old-source vs new-source comparison measures the overhaul; 1/2/4 refactored comparisons use exactly the same new engine hash. Each published workload is one measured repetition, not a statistical confidence interval.

Machine-wide CPU percentage is CPU-core equivalents divided by 16: the 100-config, four-worker run averaged 24.37% of all logical CPUs (3.90 core equivalents). CPU and aggregate RSS were sampled at 50 ms; RSS can double-count shared pages. Individual short-lived CPU activity may be missed between samples. No CPU affinity was applied.

Preflight preparation was about 0.098?0.112 s; each worker initializer (CSV loading plus immutable validation/preparation) took about 0.096?0.114 s. Final CSV/JSONL export was 0.025?0.041 s for 20 candidates and 0.100?0.109 s for 100. Interpreter/process startup is included in wall time, while initializer timings start inside the child. The JSON reports retain all individual measurements, hashes and candidate IDs. Complete compact results match exactly across 1/2/4 workers for both the 20- and 100-candidate workloads.

On the one-candidate startup probe, one worker took **0.388 s**, two-worker configuration **0.795 s**, and four-worker configuration **0.814 s**. Only one child was needed for the single queued candidate. Thus multiprocessing is slower for tiny work; the useful crossover depends on dataset size, number of candidates and cache reuse. For the measured 100-candidate prefix, four workers were **2.88x** faster than optimized sequential and **19.11x** faster than the original driver path. These are fixture results, not a guaranteed speedup on arbitrary parameter distributions or BTCUSDT history.

First-candidate cProfile (20-config benchmark): original/new full analyzer 1.076/0.503 s; CSV read 0.0247/0.0223 s; HTF coverage 0.1578/0.0330 s (5 calls to 1); indicators 0.1037/0.0626 s; convergence 0.1709/0.0246 s; signals 0.0968/0.0176 s; simulator 0.4851/0.1588 s; metrics 0.0112/0.0097 s. These inclusive stage times overlap and must not be added. Full-report CSV writing stays about 0.10 s in this profile; optimizer workers bypass it entirely.
